Codex

モデルがあってもCodex級のアプリが簡単には増えない理由

強いモデルは「実装できる範囲」を急拡大させた。しかし、Codexのような製品の難所はコード生成だけではなく、モデルを現実の環境で安全・安定・継続的に働かせる仕組みと、利用者が選ぶ理由を作ることにある。

2026.07.28 · 7 min read · 2026年7月28日確認

答え: 「モデルがあれば、原理的には多くのソフトウェアを作れる」はかなり正しい。一方で「誰でもCodex級の製品を短期間で作り、運用し、普及させられる」は別の命題である。試作品の費用は下がったが、信頼性、安全性、評価、互換性、配布、採算という残りの仕事は消えていない。

「作れる」を4段階に分ける

モデルにアプリのコードを書かせ、一度動かすところまでは急速に簡単になった。だがCodex型のアプリは、コードを返すだけでなく、利用者のファイルを読み、コマンドを実行し、途中経過を保存し、危険な操作を止め、失敗から戻り、変更をレビュー可能にする必要がある。

1. モデル 推論、コード生成、ツール選択
2. エージェント基盤 文脈、ループ、実行環境、状態管理
3. 製品 安全、評価、UX、互換性、サポート
4. 事業 顧客、流通、価格、継続利用、信用

多くの人が手にできるのは主に第1層である。APIやCodexのSDK・app-serverを使えば第2層の相当部分も借りられる。しかし、第3層と第4層は、対象ユーザーや業務ごとに設計し直さなければならない。

Codexは「モデルを呼ぶ画面」ではない

OpenAIによるCodex App Serverの解説を見ると、モデルの外側にある仕事の量が分かる。Codexの共通基盤には、モデルとツールを回すエージェントループだけでなく、スレッドの作成・再開・分岐・保存、認証と設定、進捗イベント、差分、複数クライアントとの通信が含まれる。

環境を理解して動く

OS、シェル、Git、依存関係、ビルド、テスト、リポジトリ固有ルールを発見し、長い処理の文脈を保つ。

失敗を前提に制御する

コマンド失敗、タイムアウト、通信切断、文脈の肥大化、モデルの誤判断から回復できるようにする。

危険な作用を囲う

ファイル書き込み、ネット接続、秘密情報、外部サービス操作をサンドボックス・権限・承認で制限する。

人が判断できる形にする

実行内容、変更差分、根拠、確認待ち、最終結果を、追跡・中断・レビューできるUIにする。

公式の承認とセキュリティの文書が、読み取り専用からワークスペース書き込み、承認付き操作、フルアクセスまで複数の組み合わせを定めていることも象徴的である。能力を与えるだけでは足りず、「どの作用を、どの境界内で、誰の許可により実行するか」が製品の中心になる。

なぜ「一度動く」から「毎日使える」が遠いのか

  1. モデルの能力は均一ではない

    得意な課題では驚くほど強くても、曖昧な要件、暗黙知、複数人との調整、正解を自動判定できない課題では急に不安定になる。METRも、時間幅ベンチマークは主に自己完結した明確な技術課題であり、実際の仕事はより「汚い」と注意している。

  2. 成功率は長い手順ほど積み上がる

    仮に各段階が高確率で正しくても、調査、編集、実行、修正、提出と工程が増えれば、どこかで外す可能性が増える。50%の成功率で「できる」課題と、99%近く必要な業務製品は同じではない。

  3. 自動テスト合格と製品品質は同じではない

    METRの小規模な追試では、テスト上は機能しても、テスト網羅性、整形、lint、一般的なコード品質のため、そのまま採用しにくい出力が確認された。最後の品質判断を誰がどう行うかは残る。

  4. 改善には専用の評価データが要る

    OpenAIの開発ガイドも、本番に近い入力で評価を作り、出力を継続的に測るよう勧めている。便利なデモは数例で作れるが、失敗パターンを収集し、回帰を防ぐ評価基盤は利用実績と専門知識を必要とする。

  5. 安全性と便利さが衝突する

    権限を絞ると毎回止まり、広げると誤削除、情報流出、意図しない外部操作の被害が大きくなる。誰にどこまで自動化を許すかは、単なるプロンプトでは解けない設計問題である。

  6. 作れることと、選ばれることは別

    汎用コーディングエージェントはOpenAI、Anthropic、Google、IDE企業などとの競争になり、モデル提供者が機能を標準搭載する危険もある。新規参入者には、独自の顧客接点、業務データ、連携先、専門ワークフロー、信用のいずれかが必要になる。

では、実際には誰も作っていないのか

「多くない」という観察には見え方の偏りもある。 汎用のCodex対抗製品は目立つ一方、社内の問い合わせ対応、契約書確認、テスト生成、障害調査、営業支援などに組み込まれた小さなエージェントは、単独の「AIアプリ」として見えない。さらに、既存SaaSの1機能として提供される場合も多い。

OpenAI自身も、エージェント構築には単なるモデル呼び出し以上に、ループ、ツール、ガードレール、トレース、評価が必要だとしてAgents SDKと関連基盤を提供している。これは参入障壁を下げる一方、各社が同じ土台から始めるため、「モデルをつないだだけ」では差別化しにくくなることも意味する。

小さなチームに勝ち目がある場所

Codex全体を作り直すより、CodexやAgents SDKを基盤として借り、失敗の範囲と正解を定義しやすい狭い仕事を深く解くほうが現実的である。

狙い 強い条件 弱い条件
特定業務 入力、成功条件、承認者が明確 何をもって完了か人によって違う
独自文脈 顧客データや既存システムに深く接続 公開情報だけで他社も同じ結果を出せる
評価 失敗例を集め、継続的に再テストできる 印象的なデモだけで品質を判断する
責任分界 自動実行と人の確認を明確に分ける 重要操作までモデルへ丸投げする
流通 すでに対象ユーザーへ届く経路がある 完成すれば自然に利用者が来ると考える

結論: モデルはソフトウェア開発の「実装力」を広く安価にした。しかしCodex級の価値は、モデルそのものより、実環境との接続、安全な作用、長時間の状態管理、品質評価、優れた操作体験、配布と信用を一体化したところにある。だから今後増えるのは、Codexのコピーよりも、汎用基盤の上に作られた専門的で目立たない製品だと考えるのが自然である。

根拠の限界

「なぜ起業家が参入しないか」を直接測った統計は確認できなかったため、事業上の理由は製品構造と一般的な競争条件からの解釈である。また、モデルとエージェントは急速に改善中である。METRの2025年調査では熟練開発者がAI利用時に19%遅くなったが、対象は特定の成熟したOSSと当時のツールに限られる。METRは2026年の追跡について、AIが以前より高速化に寄与している可能性を認めつつ、選択バイアスが大きく効果量は確定できないとしている。したがって、この記事は「AIは役に立たない」ではなく、「能力向上だけでは製品化の全問題は解けない」という説明である。
