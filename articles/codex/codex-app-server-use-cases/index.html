Codex

Codex app-serverとは何か、いつ使うのか

app-serverは、Codexの会話・実行・承認・進捗イベントを、自作のGUIやIDEから双方向に操作するためのローカルAPI層である。単発の自動化より、「Codexを製品の一部として見せる」用途に向く。

2026.07.25 · 8 min read · 2026年7月25日確認

ひとことで: Codex app-serverは、Codexの頭脳そのものでもWebアプリのサーバーでもない。Codexエージェントと、VS Code拡張・デスクトップアプリ・自作クライアントなどの間をつなぐ「操作プロトコルのサーバー」である。

何をしてくれるものか

OpenAI公式ドキュメントは、app-serverをCodexのリッチクライアントを動かすためのインターフェースと説明している。クライアントは、認証状態、会話履歴、モデルや設定、承認画面、コマンドやファイル編集の進行、最終回答を、それぞれ構造化されたメッセージとして扱える。

自作クライアント GUI、IDE拡張、社内ツール、別端末のTUI
JSON-RPC 要求、応答、進捗通知、承認への返答
app-server スレッド、ターン、認証、設定を管理
Codex実行環境 モデル、シェル、ファイル、MCP、スキル

通信はJSON-RPC 2.0に似た双方向プロトコルで、既定は標準入出力上の1行1JSONである。UnixソケットとWebSocketにも対応するが、WebSocketトランスポートは公式に実験的・未サポートと明記されている。

基本単位はThread・Turn・Item

単位 意味 画面での例
Thread ユーザーとCodexのひと続きの会話。新規作成、再開、分岐、一覧取得、アーカイブができる。 サイドバーに並ぶ「タスク」や「チャット」
Turn ユーザー入力からCodexの処理完了までの1往復。開始や中断ができる。 「このテスト失敗を直して」から最終報告まで
Item ターン内の細かな入出力。メッセージ、推論の要約、コマンド、ファイル編集など。 進捗カード、実行ログ、差分、回答文

接続後は最初にinitializeを送り、次にthread/startまたはthread/resume、その後turn/startを呼ぶ。実行中はitem/started、文章の差分、item/completed、最後にturn/completedなどが流れてくる。

// 概念をつかむための最小シーケンス
client → { "method": "initialize", "id": 1, "params": { "clientInfo": { ... } } }
client → { "method": "initialized" }
client → { "method": "thread/start", "id": 2, "params": { "cwd": "..." } }
client → { "method": "turn/start", "id": 3, "params": {
  "threadId": "thr_...",
  "input": [{ "type": "text", "text": "テスト失敗を調べて" }]
} }
server → { "method": "item/started", ... }
server → { "method": "item/agentMessage/delta", ... }
server → { "method": "turn/completed", ... }

コマンド実行やファイル変更に承認が必要な場合、app-serverはクライアント側へ承認要求を送る。クライアントは内容を画面に表示し、許可・拒否などを返す。このサーバーからクライアントへの要求があるため、単純な一方向HTTP APIではなく双方向通信になっている。

有効な使い道

1. 自社IDE・開発ツールへ埋め込む

チャット、変更差分、ターミナル進捗、承認ボタンを自社UIで一体化する。VS Code拡張のような体験を作りたい場合が本命である。

2. 社内Codexコンソール

複数リポジトリのスレッド一覧、実行状態、履歴、モデル、権限、レビュー待ちを、組織の運用画面へ統合する。

3. 専門用途の薄いクライアント

「CI修正だけ」「翻訳レビューだけ」など、入力項目と確認画面を業務に合わせ、裏側では通常のCodexスレッドを動かす。

4. 別マシンからTUIへ接続する

計算環境でapp-serverを動かし、手元のCodex CLIを--remoteで接続する。現時点のWebSocketは実験的なので、ローカルまたはSSH転送が安全な試用範囲である。

5. 独自の承認・監査UX

実行コマンドや変更差分を会社の承認画面に出し、許可判断をCodexへ返す。認証状態や利用量も同じクライアントで表示できる。

6. Codexクライアントの研究・試作

音声、モバイル、アクセシビリティ、可視化など、新しい操作面を試す。型定義を生成できるため、プロトコルの手書きを減らせる。

app-serverを使わないほうがよい場面

「Codexをプログラムから使う」という言葉だけではapp-serverを選ぶ理由にならない。UIの深さと、双方向イベントを自分で扱う必要があるかで決める。

やりたいこと 第一候補 理由
自作GUIで会話・差分・承認・進捗を細かく表示 app-server 認証、履歴、イベント、承認までプロトコルに含む。
CI/CDやバックエンドからCodexを継続的に制御 Codex SDK 公式もジョブ・CIにはSDKを推奨。アプリコードからスレッドを扱いやすい。
シェルスクリプトで1回実行し、最終文だけ受け取る codex exec 標準出力へ最終回答を出せるので、パイプやCIに自然に組み込める。
CodexにGitHub、Figma、ブラウザなどの道具を追加 MCP MCPはモデルへ外部ツールと文脈を渡す規格。クライアントUIを作るapp-serverとは向きが逆。
Codexをより大きな複数エージェント処理の専門役にする Codex MCP Server＋Agents SDK 公式SDKガイドが、広いオーケストレーションではこの構成を案内している。

実務上の判断: 最終回答だけ欲しければcodex exec、コードから数ターン扱うならSDK、Codexの操作画面そのものを作るならapp-server、と覚えるとよい。app-serverは最も自由だが、イベントの状態管理、再接続、承認、互換性、安全対策までクライアント側の責任が増える。

始め方

ローカル試作なら、既定の標準入出力が最も単純である。

# サーバーを標準入出力で起動
codex app-server

# 使用中のCodex版に一致するTypeScript型を生成
codex app-server generate-ts --out ./schemas

# またはJSON Schemaを生成
codex app-server generate-json-schema --out ./schemas

生成される型とスキーマは、実行したCodexのバージョンに対応する。プロトコルを記憶や古い記事から手書きせず、使用するCLIから生成するのが安全である。試作コードは子プロセスとしてcodex app-serverを起動し、標準入力へJSONLを書き、標準出力を1行ずつ読む構成にできる。

注意点

  • WebSocketは実験的: 本番システムの安定した公開APIだと見なさない。仕様変更を吸収できる設計にする。
  • ネットへ裸で公開しない: 平文WebSocketはlocalhostまたはSSHポート転送に限定する。非ローカル接続ではTLSとWebSocket認証を使う。
  • 承認を省略しない: クライアントが承認要求を正しく表示・応答できないと、安全な運用も処理の継続もできない。
  • 安定APIと実験APIを分ける: 型生成は既定で安定面だけを出す。実験機能は初期化時に明示的なオプトインが必要で、後方互換は保証されない。
  • 秘密情報をログへ出さない: 認証トークン、ユーザー入力、コマンド、ファイル内容を、デバッグログや分析基盤へ無条件に送らない。
  • SDKで足りるか先に考える: Python SDKは内部でローカルapp-serverをJSON-RPC制御する。低レベル実装が必要でなければSDKのほうが保守しやすい。
